## Знахідки

### F1 — перша сторінка ніколи не віддається: `start = page * pageSize` при `page = 1` [R11] [blocking] [critical] [confidence: high]

**Де:** `app/src/loans.js:+12` (рядки 10–14 дифу)

**Код:**
> ```js
> export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {
>   const all = listLoans(db, user);
>   const start = page * pageSize;
>   return { items: all.slice(start, start + pageSize), page, pageSize, total: all.length };
> }
> ```

**Чому це дефект:** Сторінки нумеруються з 1 (дефолт `page = 1`), а зсув обчислюється як для нумерації з 0. При `page = 1` зсув — `20`, тобто перші `pageSize` рядків пропускаються, і їх не можна отримати жодним легальним запитом. Перевірено на застосованому дифі (`createDb()` має 7 позик, `iryna` — бібліотекарка):

> `listLoansPage(db, iryna, { page: 1, pageSize: 20 })` → `{"items":[],"page":1,"pageSize":20,"total":7}`
> `listLoansPage(db, iryna)` (дефолти) → `items: []`
> `listLoansPage(db, iryna, { page: 1, pageSize: 3 })` → `items: [4,5,6]` (а не `[1,2,3]`)
> `listLoansPage(db, iryna, { page: 0, pageSize: 3 })` → `items: [1,2,3]`

Тобто UI персоналу на першій сторінці отримає порожній список при `total: 7` — рівно той екран, який PR мав полагодити. R11: опис каже «Додав `listLoansPage` — сторінки, розмір сторінки, загальна кількість», тобто обіцяє робоче сторінкування; код першу сторінку даних не повертає. Оцінюємо поведінку коду, не опис.

**Як виправити:** `const start = (page - 1) * pageSize;` і відкинути `page < 1` як помилку аргументу; закріпити тестом на `items` першої й другої сторінки.

### F2 — `pageSize` приходить від клієнта без верхньої межі, а список матеріалізується цілком [R7] [blocking] [high] [confidence: high]

**Де:** `app/src/loans.js:+10` і `:+11`

**Код:**
> ```js
> export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {
>   const all = listLoans(db, user);
> ```

**Чому це дефект:** R7 вимагає обмеженого розміру сторінки з верхньою межею **на стороні сервера**. `pageSize = 20` — лише дефолт: будь-яке значення з виклику проходить без стелі. Перевірено: `listLoansPage(db, iryna, { page: 0, pageSize: 1000000 })` повертає всі 7 позик, тобто на продакшн-даних (за описом — 3 000+ рядків) один запит із `pageSize: 1000000` віддасть увесь `db.loans` — і сторінкування не обмежує нічого. Додатково `listLoans(db, user)` щоразу будує копію **всього** списку (`rows.map((l) => ({ ...l }))`) до нарізання, тож навіть при `pageSize: 20` кожен запит сторінки копіює всі 3 000+ позик; межа, що не зменшує роботу сервера, межею не є.

**Як виправити:** затиснути розмір сторінки сервером (`const size = Math.min(Math.max(1, pageSize), MAX_PAGE_SIZE)`) і повертати в відповіді саме застосований розмір; зсув і довжину застосовувати до `db.loans` до копіювання об'єктів.

### F3 — тест стверджує лише те, що сам передав; `items` не перевіряється [R8] [blocking] [high] [confidence: high]

**Де:** `app/test/loans.test.js:+15` (рядки 36–41 дифу)

**Код:**
> ```js
> test("paged list reports the total and the page it returned", () => {
>   const res = listLoansPage(createDb(), iryna, { page: 1, pageSize: 20 });
>   assert.equal(res.total, 7);
>   assert.equal(res.page, 1);
>   assert.equal(res.pageSize, 20);
> });
> ```

**Чому це дефект:** `res.page` і `res.pageSize` — це аргументи, які тест щойно передав і які функція повертає без обчислень; `res.total` не залежить від сторінкування взагалі. Єдине, що PR реально обчислює — `items` — не перевіряється жодним твердженням. Через це дефект F1 проходить CI зеленим: тест пройшов на дифі, хоч `items` при цьому виклику — `[]`. R8: твердження не перевіряє саме те, що змінив PR.

**Як виправити:** перевіряти `res.items.map((l) => l.id)` через `assert.deepEqual` для першої й останньої сторінки при `pageSize`, меншому за кількість даних (напр. `pageSize: 3` → `[1,2,3]`, далі `[4,5,6]`, далі `[7]`).

## Прогалини стандарту

- **Немає правила про звичайну функціональну коректність.** Дефект F1 — зсув сторінки на одну сторінку вперед — це просто неправильна арифметика; у R1–R16 немає правила «код робить те, що має робити». Я провів його через R11 (опис обіцяє сторінкування, код першу сторінку не віддає), але це обхідний шлях: якби в `PR.md` не було жодного опису, найважливіша знахідка цього рев'ю формально не лягла б у жоден пункт стандарту. Варто додати правило рівня «зміна має працювати на даних, які вона обслуговує, і це закріплено тестом на результат» — або хоча б прямо сказати в стандарті, що коректність покривається через R8 (тест на конкретний результат).
- **R7 не говорить про вартість на сервері.** Правило вимагає стелі на розмір сторінки, але не забороняє матеріалізувати весь список до нарізання (`listLoans` копіює всі 3 000+ рядків на кожен запит сторінки). Формально стеля може бути на місці, а сторінкування все одно не знімає навантаження. Варто дописати до R7: зсув і межа застосовуються до джерела даних, а не до вже побудованої копії.
- **R8 детермінована частина не ловить «тест стверджує власні аргументи».** Лінтер за R8 позначає `assert.ok(` на результаті й тест без жодного `assert.strictEqual`/`assert.deepStrictEqual`; тест із F3 має три `assert.equal` і проходить фільтр, хоч не перевіряє нічого обчисленого. Варту додати перевірку «твердження не повинні звірятися лише з літералами, переданими у виклик».
