## Знахідки
### 🔴 1. Перша сторінка пропускається: зсув `page * pageSize` при нумерації з 1 — правило 14 · high
- Де: `app/src/loans.js:32`
- Доказ: > `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {` … > `const start = page * pageSize;`
- Що піде не так: сторінки за замовчуванням нумеруються з 1, але для `page = 1` зсув дорівнює `pageSize`. Наприклад, `listLoansPage(createDb(), iryna, { page: 1, pageSize: 20 })` повертає `items: []` при `total: 7`. З `pageSize: 2` перша сторінка віддає позики 3–4, а позики 1–2 не потрапляють на жодну сторінку з `page ≥ 1`. На 3 000+ рядках персонал не побачить перших `pageSize` позик.
- Також порушує: 13
- Як виправити: `const start = (page - 1) * pageSize;` і тест, що порівнює `items` з очікуваними id для першої й останньої сторінки.

### 🔴 2. Тест не перевіряє вміст сторінки й тому приховує дефект №1 — правило 8 · high
- Де: `app/test/loans.test.js:15`
- Доказ: > `assert.equal(res.total, 7);` > `assert.equal(res.page, 1);` > `assert.equal(res.pageSize, 20);`
- Що піде не так: тест перевіряє лише `total` і повернуті назад параметри `page`/`pageSize`, а `res.items` не перевіряє взагалі. Тому він зелений, хоча `items` порожній. Серйозність підвищено з medium до high, бо слабкий тест приховує дефект цього PR.
- Також порушує: —
- Як виправити: додати `assert.deepEqual(res.items.map((l) => l.id), [1, 2, 3, 4, 5, 6, 7])` для сторінки 1 і окремий випадок із малим `pageSize` (наприклад, 3), де перевіряються сторінки 1 і 3.

### 🔴 3. Розмір і номер сторінки не обмежені й не валідуються — правило 7 · medium
- Де: `app/src/loans.js:30`
- Доказ: > `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`
- Що піде не так: верхньої межі немає. `{ pageSize: 1e9 }` віддає весь список, хоча PR якраз мав прибрати проблему з 3 000+ рядків. Нечислові й від'ємні значення не відхиляються: `{ pageSize: -5 }` дає `slice(-5, -10)`, тобто `[]`; `{ page: "2" }` дає `start = 40`, а `page` у відповіді лишається рядком; `{ pageSize: NaN }` мовчки повертає `items: []`.
- Також порушує: 13
- Як виправити: перевіряти, що `page` і `pageSize` — цілі додатні числа, і кидати помилку, якщо ні; обмежити `pageSize` (наприклад, ≤ 100); додати тест на відхилення таких значень.

### 🔴 4. Нова експортована функція без запису в CHANGELOG — правило 6 · medium
- Де: `app/src/loans.js:30`
- Доказ: > `+export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {` (diff не торкається `app/CHANGELOG.md`)
- Що піде не так: з'являється новий публічний API з формою `{ items, page, pageSize, total }`, але в `app/CHANGELOG.md` про нього нічого немає.
- Також порушує: —
- Як виправити: додати запис про `listLoansPage(db, user, { page, pageSize })`: що вона повертає, з якого числа нумеруються сторінки і яка межа `pageSize`.

### 🔴 5. Немає тесту на відмову в доступі для нової функції — правило 9 · medium
- Де: `app/test/loans.test.js:15`
- Доказ: > `const res = listLoansPage(createDb(), iryna, { page: 1, pageSize: 20 });`
- Що піде не так: `listLoansPage` бере перевірку доступу з `listLoans` (персонал бачить усе, учасник — лише свої позики), але тест викликає функцію тільки від імені бібліотекарки. Немає тесту, що учасник через `listLoansPage` не бачить чужих позик і що `total` для нього не рахує чужі рядки. Якщо функцію пізніше переведуть на `db.loans` напряму, тести цього не помітять.
- Також порушує: —
- Як виправити: додати тест, що `listLoansPage(createDb(), olya)` повертає лише позики `[1, 2, 7]` і `total: 3`.
