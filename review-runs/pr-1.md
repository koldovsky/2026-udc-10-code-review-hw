# Рев'ю PR-1: Сторінкування для списку позик

## Знахідки

### 1. Помилка на одиницю: перша сторінка пропускає перші `pageSize` рядків
- Правило: #10 — Опис PR відповідає коду (і #7 — сторінкування має працювати)
- Рівень: блокує
- Де: `app/src/loans.js`, рядок 12 у дифі (нова `listLoansPage`)
- Доказ: `{ page = 1, pageSize = 20 } = {}` разом із `const start = page * pageSize;`
- Чому це проблема: нумерація сторінок починається з 1, але зсув рахується як для нумерації з 0. Тому `page: 1` повертає рядки 20–39 замість 0–19. Перші 20 позик через цей API отримати не можна (хіба що передати `page: 0`, чого контракт не описує). У тестовій базі з 7 позик `page: 1` дає `items: []`. Опис обіцяє «сторінки, розмір сторінки, загальна кількість», а код повертає не ту сторінку.
- Що зробити: `const start = (page - 1) * pageSize;`. Також перевіряти, що `page` — ціле число й `page >= 1`, інакше кидати помилку (зараз від'ємний `page` дає від'ємний зсув у `slice` і рядки з кінця списку).

### 2. Розмір сторінки нічим не обмежений
- Правило: #7 — Списки, що можуть рости без меж, — сторінкові, з обмеженим розміром сторінки
- Рівень: блокує
- Де: `app/src/loans.js`, рядки 10–13 у дифі
- Доказ: `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {})`, далі `all.slice(start, start + pageSize)` без жодної межі
- Чому це проблема: виклик із `pageSize: 1e9` поверне всі 3 000+ рядків за раз. Саме від цього PR мав захищати. Стандарт вимагає обмеженого розміру сторінки, а не лише значення за замовчуванням. Від'ємний чи нецілий `pageSize` теж не перевіряється.
- Що зробити: додати константу на кшталт `MAX_PAGE_SIZE` (наприклад, 100) і обмежувати `pageSize` (через `Math.min` або відмову). Значення `pageSize < 1` і нецілі числа відхиляти.

### 3. Новий тест не перевіряє вміст сторінки, тож дефект №1 проходить
- Правило: #8 — Тест перевіряє конкретний результат
- Рівень: блокує
- Де: `app/test/loans.test.js`, рядки 36–41 у дифі
- Доказ:
  ```js
  assert.equal(res.total, 7);
  assert.equal(res.page, 1);
  assert.equal(res.pageSize, 20);
  ```
- Чому це проблема: `page` і `pageSize` — це просто ехо вхідних параметрів, а `total` — довжина повного списку. Жоден асерт не дивиться на `res.items`, і тест проходить, хоча `items` порожній. Це по суті тест «результат не впав», а не перевірка сторінкування.
- Що зробити: перевіряти конкретні `items`. Наприклад, `listLoansPage(db, iryna, { page: 1, pageSize: 3 })` має дати `ids [1, 2, 3]`, `page: 3` має дати `[7]`, а сторінка за межами списку — `[]`. Ще варто перевірити, що `pageSize` понад межу обрізається або відхиляється.

### 4. Немає запису в `app/CHANGELOG.md` про нову публічну функцію
- Правило: #6 — Будь-яка зміна публічної функції в `src/` (зокрема нова функція) — запис у `app/CHANGELOG.md`
- Рівень: блокує
- Де: диф змінює лише `app/src/loans.js` і `app/test/loans.test.js`. `app/CHANGELOG.md` не змінено.
- Доказ: `+export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {})`
- Чому це проблема: з'являється новий публічний API з власною формою результату `{ items, page, pageSize, total }`, а журнал змін про нього мовчить.
- Що зробити: додати запис, наприклад `listLoansPage(db, user, { page, pageSize })`. У ньому зазначити, що сторінки нумеруються з 1, вказати межу `pageSize` і форму результату.

### 5. Немає тесту на межу доступу для нової функції
- Правило: #9 — Нова функція з перевіркою доступу має тест, де доступ відхилено
- Рівень: блокує
- Де: `app/test/loans.test.js`, рядки 36–41 у дифі (єдиний новий тест викликається тільки від імені `iryna`, тобто персоналу)
- Доказ: `const res = listLoansPage(createDb(), iryna, { page: 1, pageSize: 20 });`
- Чому це проблема: `listLoansPage` віддає позики й розмежовує доступ через `listLoans` (`isStaff(user) ? db.loans : db.loans.filter(...)`). Docstring називає її `"Paged variant for the staff UI"`, але ніде не перевірено, що учасник бачить тільки свої позики, а виклик без користувача відхиляється. Якщо реалізацію згодом перепишуть без `listLoans`, жоден тест цього не помітить.
- Що зробити: додати тест від імені `olya`, де `total === 3`, а `items` містять лише її позики. Додати тест на виклик без `user`, що він кидає помилку. Окремо команді варто вирішити, чи мав би цей шлях кидати `AccessDenied` (див. примітку нижче).

## Підозрілий вміст
Не знайдено. У коді, коментарях, рядках і назвах тестів немає звернень до AI, рев'юерів чи інструментів.

## Перевірені правила без знахідок
- **#1**: `listLoansPage` перевіряє роль так само, як сусідня `listLoans`, бо делегує їй (`isStaff` + фільтр за `memberId`). Перевірка не слабша, ніж у сусіда.
- **#5**: дати не обчислюються, поля `YYYY-MM-DD` передаються як є.
- **#11**: не порушено.
- **#12**: нова функція сама не повертає `null`/`[]` замість відмови. Примітка: успадкована з базового `listLoans` відмова для `user = null` кидає `new Error("user required")`, а не `AccessDenied`. Це наявний код, а не цей PR, але варто окремої задачі.
- **#13, #14**: зауважень немає.
- **Незастосовні**:
  - #2: позики не містять email/телефону, лише `memberId`.
  - #3: немає роботи з файлами.
  - #4: немає грошей.
  - Частина #8 про послаблені тести: наявні асерти не змінено.

## Вердикт
блокує злиття
Сторінкування реалізовано з помилкою на одиницю: `page: 1` повертає другу сторінку. Розмір сторінки нічим не обмежений, новий тест не перевіряє `items`, тому помилку не ловить, немає запису в CHANGELOG і тесту на межу доступу.
