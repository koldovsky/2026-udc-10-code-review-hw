### F2 — Ім'я завантаженого файлу йде у `readFile` без нормалізації й перевірки префікса [R3] [blocking] [critical] [confidence: high]

**Де:** `app/src/imports.js:18` (та `app/src/imports.js:10`)

**Код:**
> ```
> +export const UPLOAD_DIR = path.resolve("uploads");
> ...
> +  const text = await readFile(path.join(uploadDir, fileName), "utf8");
> ```

**Чому це дефект:** R3 — шлях, що приходить від користувача, потрапляє у файлову систему
без перевірки, що він лишився в дозволеній теці. `fileName` — це, за описом PR, «те ім'я,
з яким його завантажили», тобто вхід від адміністратора. `path.join` склеює, але **не
обмежує**: виклик
`importMembersFromUpload(db, admin, "../../../../etc/passwd")` дає
`readFile("/etc/passwd")` — вміст довільного файлу поза `uploads/` розбирається як CSV, а
його рядки стають записами в `db.members` (разом із F4, яке не відсіє сміття). Те саме з
`"../secret.csv"` відносно `uploadDir`. Окремо: `UPLOAD_DIR` рахується від `process.cwd()`
на момент імпорту модуля, тому «дозволена тека» залежить від того, звідки запустили
процес.

**Як виправити:** Відкидати все, крім базового імені (`path.basename(fileName)`), або
після `path.resolve(uploadDir, fileName)` перевіряти, що результат починається з
`path.resolve(uploadDir) + path.sep`, і кидати помилку інакше. `UPLOAD_DIR` задавати від
кореня застосунку, а не від `cwd`.

`мало б ловитись машиною — статичний аналіз (semgrep): `fs.*` з аргументом, похідним від параметра функції, без нормалізації й перевірки префікса`

### F3 — id нового учасника похідний від розміру колекції: після видалення id повторюється [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:23`

**Код:**
> ```
> +    db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
> ```

**Чому це дефект:** R19 — ідентифікатор нового запису мусить бути унікальним за весь час
життя колекції, а не похідним від її поточного розміру. Підстановка на даних
`createDb()` (5 учасників, id 1…5):

1. Імпорт одного рядка → `length` = 5 → новий id = **6**. Колекція: id 1,2,3,4,5,6.
2. Учасник id 3 виходить із громади, запис видалено → `length` = 5, id у колекції:
   1,2,4,5,6.
3. Імпорт ще одного рядка → `length` = 5 → новий id = **6** — **дубль** із записом із
   кроку 1.

Очікуваний результат — id 7 (жодного разу не використаний); фактичний — 6. Далі
`db.findMember(6)` (`app/src/db.js`) повертає перший збіг, тобто `memberCard` і будь-яка
видача даних за id віддасть дані не тієї людини, а `logAccess` запише доступ на чужий
`memberId`. Усередині одного імпорту дефект теж живий: якщо в колекції вже є дірка, перший
же рядок файлу отримає зайнятий id.

**Як виправити:** Видавати id з монотонного лічильника в `db` (як `addLoan`/`nextLoanId`
у `app/src/db.js`, але з лічильником, що не перераховується від довжини), наприклад
`db.addMember(...)`, який інкрементує `nextMemberId`.

`мало б ловитись машиною — лінтер-шаблон `length + 1` / `count + 1` / `size + 1` як значення поля `id``

### F4 — Рядки CSV стають записами в `db` без жодної валідації [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:19-24`

**Код:**
> ```
> +  const [, ...rows] = text.trim().split(/\r?\n/);
> +  let added = 0;
> +  for (const row of rows) {
> +    const [name, email, phone] = row.split(",");
> +    db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
> +    added++;
> ```

**Чому це дефект:** R19 — дані із зовнішнього входу стають записом у `db` лише після
перевірки, що обов'язкові поля присутні, не порожні й того типу, що очікується; інакше —
явна помилка, а не запис із `undefined`. Тут не перевіряється нічого. Підстановка на файлі

```
name,email,phone
<порожній рядок>
,,
OnlyName
X,x@example.invalid,+1,extra
```

- порожній внутрішній рядок → `"".split(",")` → `["" ]` → у `db` іде
  `{ name: "", email: undefined, phone: undefined }`;
- `,,` → `{ name: "", email: "", phone: "" }`;
- `OnlyName` (бракує стовпців) → `{ name: "OnlyName", email: undefined, phone: undefined }`;
- зайвий роздільник → `phone: "+1"`, стовпець `extra` **тихо втрачено** (а якщо в імені є
  кома — усі поля зсунуться: `"Приклад, Оля",o@x,+1` дасть `name: "\"Приклад"`,
  `email: " Оля\""`, `phone: "o@x"`).

Очікуваний результат — явна помилка й **жодного** нового запису; фактичний —
`{ added: 4 }` і чотири зіпсовані учасники в `db.members`, кожен із них далі потрапляє у
`listMembers` і `memberCard`. Окремо: `added` рахує кожен оброблений рядок незалежно від
того, чи це валідний учасник (R17 — поле відповіді не узгоджене з тим, що реально
додано).

**Як виправити:** Перед `push` перевіряти кількість стовпців і непорожність `name`,
`email`, `phone` (та формат email); на невалідному рядку — кинути помилку з номером рядка
або повернути його в списку відхилених, а не писати `undefined` у `db`. Розбір робити
парсером, що розуміє лапки, а не `split(",")`.

## Успадковані проблеми

- **Лічильник id позик ініціалізується від довжини колекції** — `app/src/db.js`,
  `let nextLoanId = loans.length + 1;`. Той самий шаблон, що в F3 (R19), але в базовому
  коді й цим дифом не змінений; до того ж там він лише початкове значення монотонного
  лічильника, а не формула на кожен запис. Не блокує цей PR (R20).

## Прогалини стандарту

- **Масове внесення персональних даних у `db` ніде не журналюється.** R2 вимагає
  `logAccess` від функції, що **повертає** email або телефон. `importMembersFromUpload`
  нічого персонального не повертає (`{ added }`), але записує email і телефон десятків
  людей у `db` — і жодного сліду «хто і коли завантажив ці дані» не лишається. Під R1–R20
  це не лягає; варто розширити R2 (або додати правило) на запис і масове внесення
  персональних даних, не лише на видачу.
- **Немає правила про дублі при імпорті.** Функція не перевіряє, чи учасник із таким
  email уже є: повторне завантаження того самого файлу створює другий набір записів тих
  самих людей. R19 говорить про унікальність id і валідацію полів, але не про природний
  ключ запису.
