## Знахідки

### F1 — експорт контактів усіх учасників доступний будь-якому автентифікованому користувачу [R1] [blocking] [critical] [confidence: high]

**Де:** `app/src/members.js:11` (додані рядки дифу, `exportMembersCsv`)

**Код:**
> ```js
> export function exportMembersCsv(db, user) {
>   if (!user) throw new AccessDenied();
> ```

**Чому це дефект:** R1 вимагає, щоб перевірка ролі була така сама, як у сусідніх функцій того самого модуля. Сусіди значно суворіші: `listMembers` викликає `requireRole(user, STAFF)` і навіть не віддає контакти (`app/src/members.js:6-7`), а `memberCard` окрім `!user` має `if (!isStaff(user) && user.id !== id) throw new AccessDenied()` (`app/src/members.js:13`). Тут єдина перевірка — що користувач не анонімний. Конкретний збій: виклик `exportMembersCsv(db, { id: 1, role: "member" })` (Оля, звичайна учасниця) повертає CSV з email і телефоном усіх 5 учасників, включно з бібліотекаркою й адміном — тобто рядовий учасник отримує те, що `listMembers` не віддає навіть персоналу, і те, що `memberCard` дозволяє йому прочитати лише про себе.

**Як виправити:** замінити `if (!user) throw new AccessDenied()` на `requireRole(user, STAFF)`, як у `listMembers`.

### F2 — персональні дані віддаються без жодного запису в журнал доступу [R2] [blocking] [critical] [confidence: high]

**Де:** `app/src/members.js:13-14` (додані рядки дифу)

**Код:**
> ```js
>   const header = "id,name,email,phone,role";
>   const lines = db.members.map((m) => [m.id, m.name, m.email, m.phone, m.role].join(","));
> ```

**Чому це дефект:** R2 вимагає `logAccess(db, user, memberId, purpose)` — **один запис на кожного учасника**, чиї email або телефон віддано. Функція повертає `m.email` і `m.phone` для всіх учасників і не викликає `logAccess` жодного разу; `import { logAccess } from "./audit.js"` у модулі є й використовується сусідньою `memberCard` (`app/src/members.js:16`), тут — ні. Конкретний збій: після `exportMembersCsv(db, iryna)` масив `db.accessLog` лишається порожнім, хоча з системи щойно вийшли контакти 5 людей. На питання «хто дивився мої дані» журнал відповість «ніхто» — найбільший за обсягом канал видачі персональних даних у модулі лишається невидимим для аудиту.

**Як виправити:** у тому самому `map` викликати `logAccess(db, user, m.id, "members-csv-export")` для кожного учасника, що потрапив у вивід.

### F3 — список, що росте з даними, віддається цілком, без сторінок і стелі [R7] [blocking] [medium] [confidence: high]

**Де:** `app/src/members.js:14` (додані рядки дифу)

**Код:**
> ```js
>   const lines = db.members.map((m) => [m.id, m.name, m.email, m.phone, m.role].join(","));
> ```

**Чому це дефект:** R7 вимагає сторінковості з обмеженим розміром сторінки для списків, що можуть рости без меж. `db.members` — саме такий список: він росте з кількістю учасників громади, і функція не має ні параметрів сторінки, ні верхньої межі. Конкретний збій: на базі з десятками тисяч учасників один виклик будує в пам'яті весь масив рядків і один великий рядок через `join("\n")` — відповідь не має стелі ні за розміром, ні за часом, і один виклик вивантажує всю базу контактів цілком.

**Як виправити:** додати серверні параметри сторінки (offset/limit) із жорсткою верхньою межею розміру сторінки, або видавати експорт порціями/потоком із фіксованим максимумом рядків на виклик.

### F4 — тест перевіряє лише форму CSV, а не те, що PR насправді змінює [R8] [blocking] [high] [confidence: high]

**Де:** `app/test/members.test.js:35-40` (додані рядки дифу)

**Код:**
> ```js
> test("CSV export has a header and one row per member", () => {
>   const csv = exportMembersCsv(createDb(), iryna);
>   const lines = csv.split("\n");
>   assert.equal(lines[0], "id,name,email,phone,role");
>   assert.equal(lines.length, 6);
> });
> ```

**Чому це дефект:** R8 вимагає, щоб твердження перевіряло саме те, що змінив PR, а не сусідній щасливий шлях. Тут перевірено лише заголовок і кількість рядків (`lines.length === 6`) — тобто форму. Не перевірено жодного рядка з даними: зміст колонок, порядок полів, екранування. Головне — не перевірено межу доступу, яку ця функція встановлює: другий тест закриває тільки анонімного викликача, а тесту на те, що звичайний учасник (`olya = { id: 1, role: "member" }`) отримує `AccessDenied`, немає — хоча саме така перевірка є у сусідів (`app/test/members.test.js:14` для `listMembers`, `:23` для `memberCard`). Конкретний збій: дефект F1 (учасник читає контакти всіх) проходить цей набір тестів зеленим — усі 15 тестів на дифі пройшли. Тест також прив'язаний до розміру seed-даних: додавання учасника в `createDb` зламає `lines.length === 6`, не вказавши на реальну проблему.

**Як виправити:** додати `assert.throws(() => exportMembersCsv(createDb(), olya), AccessDenied)` і твердження на конкретний рядок даних (`assert.equal(lines[1], "1,Оля Приклад,olya@example.invalid,+380000000001,member")`) замість підрахунку рядків; лічильник рядків виводити з `createDb().members.length`.

### F5 — опис PR подає перевірку доступу як рівну сусіднім, хоча в коді вона слабша [R11] [blocking] [medium] [confidence: high]

**Де:** `review-queue/pr-3/PR.md:4` проти `app/src/members.js:11-12` (додані рядки дифу)

**Код:**
> `PR.md`: «Без користувача — відмова, як і скрізь.»
> диф: `if (!user) throw new AccessDenied();`

**Чому це дефект:** R11 — опис PR має відповідати коду, розбіжність трактуємо на користь коду. «Як і скрізь» хибне: скрізь у цьому модулі відмова ширша за «без користувача» — `listMembers` відмовляє всім, крім `STAFF`, `memberCard` відмовляє не-персоналу на чужій картці. Конкретний збій рев'ю-процесу: формулювання описує найслабшу з можливих перевірок як відповідність нормі модуля, і рев'юер, який довіриться опису замість дифу, пропустить F1. Так само «Тест на формат файлу додав» описує рівно те, що зроблено (формат), і цим непрямо показує, що доступ і зміст даних не покриті — див. F4.

**Як виправити:** або привести код до заявленого («як і скрізь» = `requireRole(user, STAFF)`), або переписати опис так, щоб він називав фактичний обсяг доступу — тоді рішення про таке розширення ухвалюється свідомо.

## Прогалини стандарту

- **Екранування значень у текстовому форматі виводу (CSV/TSV).** `[m.id, m.name, m.email, m.phone, m.role].join(",")` не екранує коми, лапки й переводи рядка в полях. Учасник з іменем `Приклад, Оля` зсуває колонки в своєму рядку: `email` з'їжджає в `phone`, роль — у неіснуючу шосту колонку, і щомісячна звірка тихо читає чужі значення не з тих полів. Жодне з R1–R16 цього не покриває: R4 про гроші, R5 про дати, формат виводу поза ними. Варто додати правило про побудову структурованого виводу (CSV/JSON) через екранування або серіалізатор, а не конкатенацію.
- **Експорт, що вивантажує базу цілком, як окремий клас ризику.** R7 закриває лише технічну сторону (сторінки й межа); він не говорить про те, що масова видача персональних даних в один файл потребує окремого дозволу, ширшого за звичайний staff-доступ. Тут це видно: навіть із виправленим F1 будь-який бібліотекар одним викликом отримує повний контактний довідник громади. Чи потрібне окреме правило (роль `admin`, іменована мета, обов'язковий запис про сам факт експорту) — питання до команди, у стандарті його зараз немає.
