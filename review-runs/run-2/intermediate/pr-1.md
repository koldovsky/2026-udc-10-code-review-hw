Знахідки

F1 · high · блокує · Правило 15 — page * pageSize пропускає першу сторінку: page = 1 дає порожній список

- Де: app/src/loans.js:32
- Що: Сторінки рахуються з 1 ({ page = 1, pageSize = 20 }), але зсув обчислюється як для нумерації з 0: const start = page * pageSize;. Запит за замовчуванням page = 1, pageSize = 20 віддає рядки 20–39, а не 0–19. Рядки 0..pageSize-1 через жоден номер сторінки не отримати, хіба що через недокументований page = 0. Новий тест (app/test/loans.test.js:15-20) не помічає дефекту, бо перевіряє лише total, page і pageSize. Перші два параметри функція просто повертає назад, а total рахується до зрізу. items тест не перевіряє взагалі, а саме це вимагає правило 8. Тому твердження опису «Тест додав» формально правдиве, але сценарій сторінкування тест не покриває (правило 10).
- Наслідок: Бібліотекарка відкриває в UI персоналу перелік позик. Перша сторінка (page: 1) на 3 000+ рядків показує позики 21–40, а перших 20 не видно на жодній сторінці. На тестовій базі (7 позик) listLoansPage(db, iryna, { page: 1, pageSize: 20 }) повертає items: [] при total: 7. Остання сторінка за Math.ceil(total / pageSize) теж буде порожня.
- Як виправити: const start = (page - 1) * pageSize;. У тест додати перевірку вмісту, наприклад assert.deepEqual(res.items.map((l) => l.id), [1, 2, 3, 4, 5, 6, 7]) для page: 1, pageSize: 20, і другу сторінку з малим pageSize ({ page: 2, pageSize: 3 } → [4, 5, 6]).

F2 · medium · блокує · Правило 7 — page / pageSize не перевіряються, максимального розміру сторінки немає

- Де: app/src/loans.js:30
- Що: export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) бере page і pageSize як є. Немає ні верхньої межі pageSize, ні перевірки, що обидва значення цілі й додатні. Правило 7 вимагає обмежувати розмір сторінки максимумом і завжди перевіряти межі page/pageSize.
- Наслідок: Виклик із { pageSize: 100000 } віддає всі 3 000+ рядків, тобто відтворює проблему, яку PR мав прибрати. { page: -1 } дає slice(-20, 0) → []. { page: 1.5 } чи { pageSize: "20" } дають довільний або порожній зріз, а у відповіді лишається введене значення page/pageSize, тож UI не дізнається про помилку.
- Як виправити: Додати константу на кшталт MAX_PAGE_SIZE = 100. Для нецілих значень, page < 1, pageSize < 1 кидати помилку або нормалізувати їх, а pageSize обрізати до максимуму. У відповіді повертати фактично застосовані значення й покрити межі тестами.

F3 · low · блокує · Правило 6 — нова публічна функція listLoansPage без запису в app/CHANGELOG.md

- Де: app/src/loans.js:30
- Що: Диф додає export function listLoansPage(...), але app/CHANGELOG.md у дифі не змінено.
- Наслідок: Користувачі API не знають про нову функцію, її параметри (page з 1, pageSize за замовчуванням 20, максимум) і формат { items, page, pageSize, total }. Хибного результату це не дає, але правило 6 вимагає запис.
- Як виправити: Додати в app/CHANGELOG.md розділ ## 2026-10 із записом: listLoansPage(db, user, { page, pageSize }) — сторінкова версія listLoans з тими самими правами (персонал бачить усі позики, учасник лише свої). Повертає { items, page, pageSize, total }, page рахується з 1, pageSize обмежений максимумом.

Питання до автора

- JSDoc каже «Paged variant for the staff UI», але функція не викликає requireRole(user, STAFF) і через listLoans віддає учасникові його власні позики. Учасникам теж потрібне сторінкування, чи функція має бути лише для персоналу? Якщо лише для персоналу, потрібен requireRole і тест з assert.throws(..., AccessDenied) (правило 9). Якщо для всіх, варто виправити JSDoc і додати тест, що учасник через listLoansPage бачить лише свої позики.
- listLoansPage щоразу копіює весь список (listLoans робить { ...l } для всіх 3 000+ рядків) і лише потім ріже його. UI отримує менше даних, але робота на сервері росте з кількістю позик. Чи плануєте фільтрувати й різати до копіювання?
- У якому порядку повертаються позики? Порядок db.loans не задано явно. Для стабільного сторінкування при додаванні нових позик може знадобитися сортування, наприклад за id.
