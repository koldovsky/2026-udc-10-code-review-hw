Знахідки

F1 · high · блокує · Правило 15 — перша сторінка пропускає перші pageSize позик (off-by-one)

- Де: app/src/loans.js:32
- Що: Сторінки нумеруються з 1 ({ page = 1, pageSize = 20 } = {}), але зсув рахується як для нумерації з 0: const start = page * pageSize;. Для page = 1 виходить start = 20, тобто all.slice(20, 40). Позики з індексами 0–19 не потрапляють на жодну сторінку. Тест цю помилку не ловить. test/loans.test.js:15-20 («paged list reports the total and the page it returned») перевіряє лише total, а також page і pageSize, які функція просто повертає з вхідних даних. Вміст res.items тест не перевіряє взагалі (правило 8, згорнуто за правилом 19). Тому твердження опису «Додав listLoansPage — сторінки…» і «Тест додав» кодом не підтверджене (правило 10).
- Наслідок: Бібліотекарка Ірина відкриває staff UI без параметрів і отримує на першій сторінці позики 21–40. Перших 20 позик вона не побачить на жодній сторінці. На тестових даних (7 позик) listLoansPage(createDb(), iryna) повертає items: [] при total: 7. UI показує «7 позик» і порожню таблицю.
- Як виправити: const start = (page - 1) * pageSize;. У тесті перевіряти конкретний вміст, наприклад assert.deepEqual(res.items.map((l) => l.id), [1, 2, 3, 4, 5, 6, 7]) для page: 1. Додати випадок з кількома сторінками: pageSize: 3, page: 2 → id [4, 5, 6], page: 3 → [7].

F2 · medium · блокує · Правило 7 — немає максимуму pageSize і перевірки меж page/pageSize

- Де: app/src/loans.js:30-33
- Що: pageSize береться з вхідних даних без верхньої межі. page і pageSize не перевіряються на цілість і додатність: all.slice(start, start + pageSize) приймає будь-які числа. Правило 7 вимагає обмежити розмір сторінки максимумом, а для сторінкової функції межі page/pageSize перевіряються завжди.
- Наслідок: Клієнт викликає listLoansPage(db, iryna, { pageSize: 100000 }) і отримує всі 3 000+ рядків. Повертається саме та проблема, яку PR заявляє як розв'язану («у UI все гальмує»). За page: 0 після виправлення F1 вийде slice(-20, 0), тобто []. За від'ємного pageSize повертається порожньо або щось незрозуміле. Помилки про некоректний запит клієнт не отримує.
- Як виправити: Додати константу, наприклад MAX_PAGE_SIZE = 100. Якщо page або pageSize не цілі, або page < 1, або pageSize < 1, кидати помилку. Розмір сторінки обмежувати через Math.min(pageSize, MAX_PAGE_SIZE) (або відхиляти завеликий). Додати тести на ці межі.

F3 · low · блокує · Правило 6 — нова публічна функція без запису в CHANGELOG

- Де: app/src/loans.js:30 (export function listLoansPage)
- Що: Диф додає export-функцію listLoansPage(db, user, { page, pageSize }) з результатом { items, page, pageSize, total }, але app/CHANGELOG.md у дифі не змінено.
- Наслідок: Користувачі API не дізнаються про нову функцію, її параметри, нумерацію сторінок і формат результату. Хибного результату для користувача це не дає.
- Як виправити: Додати в app/CHANGELOG.md запис у розділ поточного місяця. У ньому вказати сигнатуру, базу нумерації page (з 1), значення за замовчуванням і максимум pageSize, поля результату і правила доступу (як у listLoans).

Питання до автора

- JSDoc каже «Paged variant for the staff UI», опис — «Список позик для персоналу». Сама функція не вимагає ролі персоналу: вона делегує в listLoans, тому учасник отримує сторінки зі своїми позиками. Відкритішою за listLoans вона від цього не стає, тому це не знахідка. Але чи це задумано? Якщо функція має бути лише для персоналу, потрібні requireRole(user, STAFF) і тест з assert.throws(..., AccessDenied) (правила 1, 9). Якщо доступ має бути як у listLoans, варто додати тест, що учасник бачить на сторінці лише свої позики.
- За user = null функція кидає загальний Error("user required"), а не AccessDenied. Це успадковано від listLoans і цим PR не введено. Чи планується узгодити тип помилки (правило 15)?
- Кожен виклик сторінки копіює всі позики через listLoans, тобто rows.map((l) => ({ ...l })) на всі 3 000+ рядків, і лише потім ріже slice. Для заявленого обсягу це, мабуть, прийнятно. Чи не краще спершу зробити slice і копіювати лише сторінку?
- Сортування не задано: порядок сторінок залежить від порядку в db.loans. Чи потрібен стабільний порядок (наприклад, за id чи dueAt), щоб сторінки не «пливли» після нових позик?
