### F1 — ім'я завантаженого файлу йде у `readFile` без нормалізації й перевірки префікса [R3] [blocking] [critical] [confidence: high]

**Де:** `app/src/imports.js:18`

**Код:**
> ```js
> export async function importMembersFromUpload(db, user, fileName, { uploadDir = UPLOAD_DIR } = {}) {
>   requireRole(user, ["admin"]);
>   const text = await readFile(path.join(uploadDir, fileName), "utf8");
> ```

**Чому це дефект:** R3 — шлях, що приходить від користувача, не потрапляє у файлову систему
без перевірки, що він лишився в дозволеній теці. `fileName` — це «ім'я, з яким файл
завантажили» (так сказано і в `PR.md`, і в докблоці `imports.js:14`), тобто рядок із
зовнішнього входу. `path.join` не є перевіркою: він спокійно склеює підйоми вгору.
Підстановка: `importMembersFromUpload(db, admin, "../../../../etc/passwd")` →
`path.join("<repo>/uploads", "../../../../etc/passwd")` = `/etc/passwd` → `readFile` читає
цей файл, перший рядок відкидається як заголовок, а решта рядків стає записами в
`db.members` (`{ name: "daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin", email: undefined, … }`).
Два збої одним викликом: довільне читання файлів поза `uploads/` і засмічення `db.members`
вмістом цього файлу. Жодної перевірки на `path.resolve(...).startsWith(UPLOAD_DIR + path.sep)`
у дифі немає, хоча `UPLOAD_DIR` поруч оголошено (`imports.js:10`) — отже нормалізація
задумувалась, але не дописана.

**Як виправити:** `const full = path.resolve(uploadDir, fileName);` і відмовляти
(`throw new Error("bad upload path")`), якщо `full` не починається з `path.resolve(uploadDir) + path.sep`;
додатково відкинути `fileName`, що містить `path.sep` або `..`.

`мало б ловитись машиною — статичний аналіз R3 (semgrep: fs.* з аргументом, похідним від параметра функції, без нормалізації й перевірки префікса)`

### F3 — id нового учасника похідний від розміру колекції: `db.members.length + 1` [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:23`

**Код:**
> ```js
> db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
> ```

**Чому це дефект:** R19 — ідентифікатор нового запису має бути унікальним за весь час життя
колекції, а не похідним від її поточного розміру: видалення робить такий id повторним.
Сценарій «додали, видалили, додали» на сідових даних (`app/src/db.js:5-11`, учасники
id 1…5, `length` = 5):

1. Імпорт файлу з двома рядками → `id` = 5+1 = **6** і 6+1 = **7**; `db.members.length` = 7
   (саме це й фіксує новий тест, `app/test/imports.test.js:76`).
2. Учасника з `id` 3 виключають із громади → `db.members.length` = 6, наявні id: 1, 2, 4, 5, 6, 7.
3. Імпорт файлу з одним рядком → `id` = 6+1 = **7** — другий запис із тим самим id.

Далі `db.findMember(7)` (`app/src/db.js:41`) повертає **перший** знайдений запис, тобто
старого учасника: `memberCard(db, user, 7)` віддасть email і телефон не тієї людини, а
новий учасник стане недосяжним за своїм id. Поруч у тому самому `db.js` уже є правильний
зразок — `let nextLoanId = loans.length + 1` плюс `id: nextLoanId++` (`db.js:34`, `db.js:48`):
монотонний лічильник, що не залежить від видалень. Диф його не використав.

**Як виправити:** додати в `createDb` лічильник `nextMemberId` і метод `addMember(member)`
за зразком `addLoan`, а в імпорті викликати `db.addMember(...)` замість `db.members.push`
із самостійно порахованим id.

`мало б ловитись машиною — лінтер-шаблон "length + 1 як id" (детермінована частина R19)`

### F4 — рядок CSV стає записом у `db` без жодної валідації [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:21-24`

**Код:**
> ```js
>   for (const row of rows) {
>     const [name, email, phone] = row.split(",");
>     db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
>     added++;
>   }
> ```

**Чому це дефект:** R19 — дані із зовнішнього входу стають записом у `db` лише після
перевірки: обов'язкові поля присутні й не порожні, типи ті, що очікуються; інакше — явна
помилка, а не запис із `undefined`. Тут між `split(",")` і `push` немає нічого: що
розібралось, те й записано. Підстановка, файл `new-members.csv`:

```
name,email,phone
Нова Учасниця,new1@example.invalid,+380000000010

Новий Учасник
```

`text.trim().split(/\r?\n/)` дає `rows` = `["Нова Учасниця,new1@…,+380…", "", "Новий Учасник"]`:

- порожній рядок: `"".split(",")` = `[""]` → у `db.members` падає
  `{ id: 7, name: "", email: undefined, phone: undefined, role: "member" }`;
- рядок без двох стовпців: → `{ id: 8, name: "Новий Учасник", email: undefined, phone: undefined }`.

Очікуваний результат: явна помилка (або щонайменше пропуск) і `{ added: 2 }`.
Фактичний: `{ added: 3 }` і два зламані учасники в базі. Наслідки видно одразу в сусідніх
функціях: `listMembers` (`app/src/members.js:5`) показує персоналу учасника з порожнім
ім'ям, `memberCard` (`members.js:17`) віддає `email: undefined`, `phone: undefined` —
і при цьому пише запис у журнал доступу, ніби дані віддано.

Друга підстановка — кома в полі (докблок обіцяє звичайний `name,email,phone`, але розбір
не знає про лапки). Рядок `"Приклад, Оля",olya@example.invalid,+380000000012`:
`split(",")` дає `name` = `"Приклад`, `email` = ` Оля"`, `phone` = `olya@example.invalid`.
Очікувано: `name` = `Приклад, Оля`, `email` = `olya@example.invalid`, `phone` = `+380…`.
Фактично — телефон людини втрачено, в полі email лежить уривок імені; `memberCard`
віддає це як контакт учасника.

**Як виправити:** перед `push` перевіряти розібраний рядок: рівно три непорожні поля
після `trim`, email за мінімальним шаблоном; рядок, що не пройшов, — явна помилка з
номером рядка (або накопичений список `skipped`, якщо продовжувати імпорт свідомо
вирішено), і він не має потрапляти в `added`.

## Прогалини стандарту

- **Немає правила про межі на вхідні дані.** R7 говорить про список, який система
  **віддає** («сторінковий, з обмеженим розміром сторінки»). Про обсяг, який система
  **приймає** — розмір завантаженого файлу, кількість рядків в одному імпорті, кількість
  записів, які один виклик може додати в `db` — у R1–R20 не сказано нічого. F6 довелося
  тягнути через R7 + R20, і саме тому там `confidence: low`. Варто окреме правило:
  операція, що приймає зовнішній файл або пакет записів, має явний максимум на стороні
  сервера.
- **Немає правила про формат розбору зовнішніх даних.** R19 покриває «поле порожнє / не
  того типу», але не покриває випадок, коли розбір узагалі не той: `split(",")` замість
  CSV-розбору з лапками (друга підстановка у F4) дає **заповнені, валідні за типом, але
  переставлені** поля — email у полі телефону. Це проходить будь-яку перевірку
  «обов'язкові поля присутні й не порожні». Формально я лишив це в F4 під R19, але правило
  говорить про валідацію значень, а не про коректність розбору.
