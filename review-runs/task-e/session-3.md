### F3 — id нового учасника — `db.members.length + 1`: після видалення id повторюється [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:23`

`addLoan` — диф цей наявний поряд патерн не використав.

**Як виправити:** Додати в `createDb` такий самий монотонний `nextMemberId` і функцію
`addMember`, і писати учасників через неї, а не `push` з обчисленим id.

`мало б ловитись машиною — лінтер-шаблон `length + 1` як значення поля `id` (та дрібниця з

### F4 — Рядок CSV стає записом у `db` без жодної валідації: учасник з порожнім іменем і `undefined` email/телефоном [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:21-24`

**Код:**
> ```js
> for (const row of rows) {
>   const [name, email, phone] = row.split(",");
>   db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
>   added++;
> }
> ```

**Чому це дефект:** R19: дані із зовнішнього входу стають записом у `db` лише після
перевірки, що обов'язкові поля присутні й не порожні, — інакше має бути явна помилка, а не
запис із `undefined`. Тут немає ні перевірки кількості стовпців, ні перевірки на порожнє
значення, ні перевірки, що перший рядок справді заголовок. Підставлено й прогнано два
входи:

- порожній рядок усередині файлу (`"name,email,phone\nA,a@x.invalid,+1\n\nB,b@x.invalid,+2\n"`)
  — `"".split(",")` дає `[""]`, і в `db.members` ліг
  `{"id":7,"name":"","role":"member"}`: полів `email` і `phone` у записі немає взагалі
  (`undefined` не серіалізується);
- рядок із бракуючим стовпцем (`"name,email,phone\nC\n"`) — у `db.members` ліг
  `{"id":6,"name":"C","role":"member"}`, знову без email і телефону.

Конкретний збій далі по коду: `memberCard(db, staff, 6)` повертає
`{ id: 6, name: "C", email: undefined, phone: undefined }` і при цьому пише запис у журнал
доступу, тобто API віддає заповнену карточку учасника, якого насправді не імпортували. Ще
один шлях: файл без рядка заголовка — `app/src/imports.js:19` беззастережно викидає перший
рядок (`const [, ...rows] = ...`), тому з двох справжніх рядків імпортується один, а
перший учасник зникає без жодної помилки.

**Як виправити:** Перед `push` перевіряти рядок: рівно три непорожні поля після `trim`,
інакше — кинути помилку з номером рядка (або зібрати список відкинутих рядків у
результат). Заголовок перевіряти на очікувані назви стовпців, а не викидати наосліп.

### F5 — `added` не збігається з кількістю справді імпортованих учасників [R17] [blocking] [medium] [confidence: high]

**Де:** `app/src/imports.js:20-26`

**Код:**
> ```js
> let added = 0;
> for (const row of rows) {
>   ...
>   added++;
> }
> return { added };
> ```

**Чому це дефект:** R17: поля однієї відповіді мають бути узгоджені з тим, що код
насправді зробив, і це перевіряється підстановкою, а не читанням. `added` рахує **ітерації
циклу**, а не додані записи, тому будь-який рядок-сміття роздуває лічильник. Підставлено й
прогнано: файл `"name,email,phone\nA,a@x.invalid,+1\n\nB,b@x.invalid,+2\n"` (два
справжніх учасники й один порожній рядок) — **очікувано** `{ added: 2 }`, **фактично**
`{ added: 3 }`, а в `db.members` три нові записи, третій з яких — порожній (див. F4).
Межові значення перевірено окремо й там розбіжності немає: файл лише із заголовком
(`"name,email,phone\n"`) → `rows = []` → `{ added: 0 }`, і повністю порожній файл
(`""` → `trim()` → `[""]` → `rows = []`) → `{ added: 0 }` — обидва коректні.
Адміністратор, який бачить «додано 3», не має способу дізнатися, що один із трьох —
непридатний запис.

**Як виправити:** Інкрементувати `added` лише після успішної валідації й запису рядка
(після виправлення F4), а відкинуті рядки повертати окремим полем, щоб відповідь сходилась
із тим, що в `db`.

## Прогалини стандарту

- **Масове занесення персональних даних не покрите R2.** R2 вимагає `logAccess` від
  функції, яка **повертає** email або телефон. `importMembersFromUpload` нічиїх
  персональних даних не повертає (`return { added }`), але заносить у `db` email і
  телефони довільної кількості людей — і жодного сліду «хто і коли завантажив ці дані» не
  лишається. Питання «хто і навіщо дивився мої дані» з `docs/team-conventions.md` має
  парну половину — «хто і звідки взяв мої дані», — і правила під неї в стандарті немає.
  Формально знахідки тут немає; це пункт для наступної ревізії стандарту, а не для
  severity.
- **Стеля на обсяг зовнішнього входу не названа явно.** R7 говорить про сторінковість
  **списку у відповіді**, R19 — про валідацію **полів** запису. Кількість рядків у
  завантаженому файлі не покриває ні перше, ні друге: 100 000 рядків — це коректні поля й
  порожня відповідь `{ added: 100000 }`. F9 пришито до R7 через R20, але точнішим було б
  окреме правило «зовнішній вхід має явну межу обсягу».
