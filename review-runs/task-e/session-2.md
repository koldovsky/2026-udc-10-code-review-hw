### F1 — ім'я завантаженого файлу йде у `readFile` без нормалізації й перевірки префікса [R3] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:18` (додані рядки дифу; функція `importMembersFromUpload`)

**Код:**
> ```js
> export async function importMembersFromUpload(db, user, fileName, { uploadDir = UPLOAD_DIR } = {}) {
>   requireRole(user, ["admin"]);
>   const text = await readFile(path.join(uploadDir, fileName), "utf8");
> ```

**Чому це дефект:** R3 — шлях, що приходить від користувача, потрапляє у файлову систему без
перевірки, що він лишився в дозволеній теці. `fileName` — це, за описом PR, «ім'я, з яким
файл завантажили», тобто значення з зовнішнього входу. `path.join` не обрізає `..`:
`path.join("/repo/uploads", "../../etc/passwd")` дає `/etc/passwd` (для абсолютного
`fileName` ескейпу немає — `path.join` склеює його всередину теки, тож небезпечний саме
`../`). Конкретний збій: виклик
`importMembersFromUpload(db, admin, "../../etc/passwd")` читає файл поза `uploads/`,
розбиває його по рядках і пушить у `db.members` — після чого `listMembers` (`app/src/members.js:5`,
доступна будь-якому `STAFF`, не лише admin) віддає вміст цього файлу в полі `name`. Тобто
право «admin імпортує CSV» перетворюється на «читання довільного файлу з диска через API,
з видачею бібліотекарям». Додатково: дозволена тека `UPLOAD_DIR = path.resolve("uploads")`
залежить від `process.cwd()`, а четвертий параметр `{ uploadDir }` дозволяє викликачу
підмінити саму дозволену теку — отже навіть доданий потім префіксний чек ні від чого не
захищає, доки `uploadDir` приходить від викликача.

**Як виправити:** обчислити `const full = path.resolve(uploadDir, fileName)` і відмовити
(`throw`), якщо `full` не починається з `path.resolve(uploadDir) + path.sep`; `uploadDir`
не брати з аргументів публічної функції (лишити лише для тестів через внутрішню функцію
або приймати не шлях, а вже перевірений дескриптор завантаження).

`мало б ловитись машиною — статичний аналіз (semgrep-правило R3: fs.* з аргументом, похідним від параметра функції, без нормалізації й перевірки префікса)`

### F3 — id нового учасника похідний від розміру колекції: `db.members.length + 1` [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:23` (доданий рядок дифу)

**Код:**
> ```js
> db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
> ```

**Чому це дефект:** R19 — ідентифікатор нового запису має бути унікальним за весь час життя
колекції, а не похідним від її поточного розміру: видалення робить такий id повторним.
Сценарій на сидових даних `createDb()` (`app/src/db.js`), де `members` — 5 записів з id 1…5,
а `loans` містять `{ id: 5, memberId: 5, … }` і `{ id: 6, memberId: 5, … }` (книжки Марка
Приклада, id 5):

1. додали — імпорт дає id 6;
2. видалили учасника з id 5 → `db.members.length` стає 5 (6 мінус один);
3. додали ще один рядок CSV → `id = 5 + 1 = 6`, а учасник з id 6 уже існує з кроку 1.

А якщо видалити id 5 до першого імпорту: `length` = 4 → новий учасник отримує `id = 5`,
і `db.findMember(5)` віддає нову людину, до якої тепер прив'язані позики `memberId: 5`
старого Марка; `memberCard(db, user, 5)` покаже її email і телефон під чужою історією
позик. Тобто це не лише дубль ключа, а підміна власника записів.

**Як виправити:** видавати id з монотонного лічильника в `db` (як уже зроблено для позик —
`nextLoanId` у `app/src/db.js`), додавши `db.addMember(...)` поряд з наявним `db.addLoan(...)`,
і пушити учасників через нього, а не напряму в масив.

`мало б ловитись машиною — лінтер-шаблон «length + 1 / count + 1 / size + 1 як id» (детермінована частина R19)`

### F4 — розібрані рядки CSV стають записами в `db` без жодної валідації [R19] [blocking] [high] [confidence: high]

**Де:** `app/src/imports.js:19-25` (додані рядки дифу)

**Код:**
> ```js
> const [, ...rows] = text.trim().split(/\r?\n/);
> let added = 0;
> for (const row of rows) {
>   const [name, email, phone] = row.split(",");
>   db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });
>   added++;
> }
> ```

**Чому це дефект:** R19 — дані із зовнішнього входу стають записом у `db` лише після перевірки,
що обов'язкові поля присутні, не порожні й того типу, який очікується; інакше потрібна явна
помилка, а не запис із `undefined`. Тут не перевіряється нічого: ні кількість стовпців, ні
непорожність, ні формат. Підстановка (семантика `String.prototype.split` і деструктуризації):

| рядок у CSV | що потрапляє в `db.members` | що мало б бути |
|---|---|---|
| `Лише Імя` (без ком) | `{ name: "Лише Імя", email: undefined, phone: undefined }` | явна помилка «бракує стовпців» |
| порожній рядок усередині файлу | `{ name: "", email: undefined, phone: undefined }` | рядок пропущено або помилка |
| `,,` | `{ name: "", email: "", phone: "" }` | явна помилка «порожні обов'язкові поля» |
| `"Приклад, Оля",olya@example.invalid,+380000000099` | `{ name: "\"Приклад", email: " Оля\"", phone: "olya@example.invalid" }` — телефон втрачено, email поїхав у поле `phone` | `name: "Приклад, Оля"`, email і телефон на своїх місцях |

Наслідки конкретні: `memberCard` потім віддає `email: undefined` або email у полі `phone`
(`app/src/members.js:17`), а `listMembers` — учасника з порожнім іменем. Останній рядок
таблиці — звичайна CSV з комою в імені, тобто типовий, а не екзотичний вхід: роздільник не
екранується й не враховуються лапки. Поле `added` при цьому рахує всі рядки, включно зі
сміттєвими (перевірив межі: файл лише з шапкою → `added: 0`, порожній файл → `added: 0`,
один рядок → `added: 1` — сама арифметика лічильника правильна, але вона рахує не «додано
учасників», а «побачено рядків»).

**Як виправити:** перед `push` перевіряти, що рядок дав рівно три непорожні поля очікуваного
вигляду (email з `@`), і на невалідному рядку кидати явну помилку з номером рядка (або
повертати `{ added, rejected }` з переліком рядків); розбір робити парсером, що розуміє
лапки, а не `split(",")`.

## Успадковані проблеми

- **`db.addLoan` виводить початковий id з довжини колекції** — `app/src/db.js`:
  `let nextLoanId = loans.length + 1`. Споріднено з R19, але це лічильник, який далі лише

## Прогалини стандарту

- **Немає правила про обсяг даних, що входять у систему.** R7 покриває лише списки, які
  система **віддає** (сторінки, стеля розміру). Тут же `readFile(..., "utf8")` зачитує
  завантажений файл у пам'ять цілком і вставляє необмежену кількість записів у `db` одним
  викликом, без ліміту на розмір файлу чи кількість рядків. Це виглядає дефектом (файл на
  гігабайт кладе процес), але під жодне з R1–R20 не лягає: R7 — про вихід, R18 — про вартість
  пошуку в циклі (тут його немає: усередині циклу лише `push` і `db.members.length`, O(1),
  готового індексу диф ні на що не замінював). Пропоную в наступній ітерації стандарту
  розширити R7 до «межі на вхід і на вихід».
