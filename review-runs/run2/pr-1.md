# Рев'ю PR-1: Сторінкування для списку позик

## Знахідки

### 1. Через помилку на одиницю в зсуві перша сторінка недосяжна за замовчуванням, а сторінка 1 повертає не ті записи
- Правило: #10: Опис PR відповідає коду
- Рівень: блокує
- Впевненість: висока
- Де: `review-queue/pr-1/change.diff:10-12` (`app/src/loans.js`, нова `listLoansPage`)
- Доказ: `{ page = 1, pageSize = 20 } = {}` разом із `const start = page * pageSize;`
- Чому це проблема: сторінки нумеруються з 1, а зсув рахується як для нумерації з 0. Тому `page: 1` пропускає перші `pageSize` записів. На тестових даних (7 позик) `listLoansPage(db, iryna, { page: 1, pageSize: 20 })` поверне `items: []` і водночас `total: 7`. В опис PR обіцяє робоче сторінкування, а персонал на першій сторінці нічого не побачить.
- Що зробити: `const start = (page - 1) * pageSize;` і додати тест на вміст `items` (див. знахідку 2).

### 2. Новий тест перевіряє лише значення, які функція повертає без змін, а не самі записи сторінки
- Правило: #8: Тест перевіряє конкретний результат
- Рівень: блокує
- Впевненість: висока
- Де: `review-queue/pr-1/change.diff:36-41` (`app/test/loans.test.js`)
- Доказ: `assert.equal(res.total, 7); assert.equal(res.page, 1); assert.equal(res.pageSize, 20);`
- Чому це проблема: `page` і `pageSize` просто повертаються з вхідних параметрів, а `total` дорівнює `listLoans(...).length`, і це вже покрито тестом «staff see every loan». `items` тест не перевіряє взагалі, тому помилка зі знахідки 1 проходить зелено.
- Що зробити: додати `assert.deepEqual(res.items.map((l) => l.id), [...])` для першої й наступної сторінки (наприклад, `pageSize: 3` → `[1, 2, 3]`, потім `[4, 5, 6]`, потім `[7]`). Додати також перевірку, що учасник через `listLoansPage` бачить лише свої позики.

### 3. Розмір сторінки не має верхньої межі, а `page`/`pageSize` ніяк не перевіряються
- Правило: #7: Списки, що можуть рости без меж, — сторінкові, з обмеженим розміром сторінки
- Рівень: блокує
- Впевненість: висока
- Де: `review-queue/pr-1/change.diff:10-13`
- Доказ: `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {` і `all.slice(start, start + pageSize)`
- Чому це проблема: клієнт може передати `pageSize: 1e9` і отримати весь список одним запитом, тобто проблему, яку PR мав прибрати. Від'ємні, нульові чи дробові значення дають неочевидні результати: `slice` з від'ємним `start` рахує з кінця масиву, а `pageSize: 0` дає порожню сторінку.
- Що зробити: обмежити `pageSize` (наприклад, `Math.min(pageSize, 100)`), вимагати цілі `page >= 1` і `pageSize >= 1`, а на некоректні значення відповідати відмовою чи нормалізацією. Покрити це тестом.

### 4. Нова публічна функція без запису в `app/CHANGELOG.md`
- Правило: #6: Зміна того, що приймає/повертає публічна функція, має запис у `app/CHANGELOG.md`
- Рівень: блокує
- Впевненість: висока
- Де: `app/CHANGELOG.md` (у дифі не змінений); нова функція в `review-queue/pr-1/change.diff:10`
- Доказ: дифф змінює лише `app/src/loans.js` і `app/test/loans.test.js`; `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {})`
- Чому це проблема: за стандартом кожна нова публічна функція в `src/` має запис у тому самому PR, і запис має збігатися з сигнатурою, зокрема з об'єктом опцій і формою результату.
- Що зробити: додати запис на кшталт ``- `listLoansPage(db, user, { page = 1, pageSize = 20 })` → `{ items, page, pageSize, total }`; staff see every loan, a member only their own; page is 1-based, pageSize ≤ N.``
