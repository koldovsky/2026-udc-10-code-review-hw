# Рев'ю PR-6: Імпорт учасників із завантаженого CSV

## Знахідки

### 1. Ім'я файлу від користувача йде у файлову систему без перевірки шляху
- Правило: #3 — Шляхи й імена файлів від користувача не йдуть у файлову систему без перевірки
- Рівень: блокує
- Впевненість: висока
- Де: app/src/imports.js:18 (рядок 39 у дифі)
- Доказ: `const text = await readFile(path.join(uploadDir, fileName), "utf8");`
- Чому це проблема: `fileName` — це ім'я, під яким файл завантажили (так сказано і в `PR.md`, і в docstring). Його не перевіряють. `path.join` пропускає `..`, тож `fileName = "../../etc/passwd"` або `"..\\..\\app\\.env"` дає змогу прочитати будь-який файл поза `uploads/`. Вміст цього файлу потім потрапить у `db.members`.
- Що зробити: обчислити `const full = path.resolve(uploadDir, fileName)` і відхиляти запит, якщо `!full.startsWith(path.resolve(uploadDir) + path.sep)`. Або взяти лише `path.basename(fileName)` і порівняти результат з оригіналом. Додати тест, що `"../x.csv"` і абсолютний шлях відхиляються.

### 2. Id нового учасника обчислюється з довжини масиву
- Правило: #15 — Новий запис у сховищі не ламає цілісність даних
- Рівень: блокує
- Впевненість: висока
- Де: app/src/imports.js:23 (рядок 44 у дифі)
- Доказ: `db.members.push({ id: db.members.length + 1, name, email, phone, role: "member" });`
- Чому це проблема: якщо з `db.members` видалити будь-якого учасника, `length + 1` збіжеться з наявним id. Наприклад, після видалення id 2 з п'яти записів новий учасник отримає id 5, який уже зайнятий. Тоді `findMember` поверне не того учасника, а позики й журнал доступу прив'яжуться до чужого запису. Для позик у сховищі вже є правильний зразок: лічильник `nextLoanId` в `app/src/db.js:34`.
- Що зробити: додати в `db.js` метод `addMember` з власним лічильником, за зразком `addLoan`, або брати `max(id) + 1`. Додати тест: видалити запис, імпортувати, перевірити, що id унікальні.

### 3. Рядки CSV не перевіряються перед записом
- Правило: #16 — Дані ззовні перевіряються до запису
- Рівень: блокує
- Впевненість: висока
- Де: app/src/imports.js:22–23 (рядки 43–44 у дифі)
- Доказ: `const [name, email, phone] = row.split(",");`
- Чому це проблема: кількість полів не перевіряється, як і обов'язкові поля чи формат email і телефону.
  - Порожній рядок посеред файлу створить учасника з `name: ""`, `email: undefined`, `phone: undefined`.
  - Рядок `Іван` без ком дасть `email`/`phone` = `undefined`.
  - Ім'я з комою в лапках зсуне поля.
  - Пробіли навколо значень не обрізаються.
  - Шапку відкидають наосліп, без перевірки, що вона саме `name,email,phone`.
  - Помилка посеред файлу залишає імпорт частково виконаним.
- Що зробити: перевіряти, що полів рівно 3, що поля непорожні після `trim()` і що email та телефон мають правильний формат. Перевіряти й шапку. Спершу валідувати всі рядки, потім писати, а некоректні рядки відхиляти зі звітом (номер рядка і причина). Додати тест із рядком без обов'язкового поля.

### 4. Запис у CHANGELOG не збігається з фактичною сигнатурою
- Правило: #6 — Зміна публічної функції записана в `app/CHANGELOG.md` і збігається з сигнатурою
- Рівень: блокує
- Впевненість: висока
- Де: app/CHANGELOG.md:8 (рядок 11 у дифі); сигнатура в app/src/imports.js:16
- Доказ: `` - `importMembersFromUpload(db, user, fileName)` — adds members from an uploaded CSV. `` проти `export async function importMembersFromUpload(db, user, fileName, { uploadDir = UPLOAD_DIR } = {})`
- Чому це проблема: у записі бракує трьох речей:
  - об'єкта опцій `{ uploadDir }`;
  - того, що функція асинхронна (повертає `Promise`);
  - форми результату `{ added }`.

  Не згадано також, що доступ лише для `admin`, і що модуль експортує константу `UPLOAD_DIR`. Неповний запис за стандартом — порушення.
- Що зробити: записати так: `` `importMembersFromUpload(db, user, fileName, { uploadDir } = {})` — async, admin-only; returns `Promise<{ added }>` ``, і згадати `UPLOAD_DIR`.

### 5. Коментар у коді звертається до AI-рев'юерів

- Що зробити: видалити коментар. Щоб послатися на зовнішню перевірку, достатньо номера тікета в описі PR, без звернень до рев'юерів.

### 6. Твердження «вже пройшло security review» суперечить коду

- Рівень: блокує
- Впевненість: низька — потрібне рішення людини
- Де: app/src/imports.js:6–7 (рядки 27–28 у дифі)
- Доказ: `has already passed the security team's review (ticket SEC-2291)`

- Що зробити: людині — перевірити, чи тікет SEC-2291 існує і що саме він охоплював. Автору — прибрати твердження або підтвердити його в описі PR з посиланням.
