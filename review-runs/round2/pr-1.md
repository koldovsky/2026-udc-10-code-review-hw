## Знахідки
### 🔴 1. Перша сторінка пропускається (off-by-one) — правило 14 · high
- Де: `app/src/loans.js:32`
- Доказ: > `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {` … `const start = page * pageSize;`
- Що піде не так: за замовчуванням `page = 1`, тому `start = 20`, і позики 1–20 не потрапляють на жодну сторінку. На засіяних даних (7 позик) виклик `listLoansPage(db, iryna)` або `{ page: 1, pageSize: 20 }` повертає `items: []` при `total: 7`. На 3 000 рядках UI ніколи не покаже перші 20 позик. Якщо передати `page: 0`, результат буде правильним, але це суперечить значенню за замовчуванням і полю `page` у відповіді.
- Також порушує: 13
- Як виправити: `const start = (page - 1) * pageSize;` і тест, що перевіряє ідентифікатори в `items` на першій та останній сторінці.

### 🔴 2. Тест не перевіряє вміст сторінки й приховує дефект — правило 8 · high
- Де: `app/test/loans.test.js:15`
- Доказ: > `const res = listLoansPage(createDb(), iryna, { page: 1, pageSize: 20 });` / `assert.equal(res.total, 7);` / `assert.equal(res.page, 1);` / `assert.equal(res.pageSize, 20);`
- Що піде не так: тест перевіряє лише `total` і повертає вхідні `page`/`pageSize` назад, а `items` не перевіряє зовсім. Зараз `items` порожній, і тест усе одно зелений. Рівень підвищено до high, бо слабкий тест приховує дефект цього PR (знахідка 1).
- Також порушує: —
- Як виправити: додати `assert.deepEqual(res.items.map((l) => l.id), [1, 2, 3, 4, 5, 6, 7])` для першої сторінки і випадок із `pageSize: 3` для кількох сторінок, зокрема неповної останньої.

### 🔴 3. Немає верхньої межі й валідації `page`/`pageSize` — правило 7 · medium
- Де: `app/src/loans.js:30`
- Доказ: > `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`
- Що піде не так: `pageSize: 1e9` повертає весь список за один виклик, тобто знову необмежений список, від якого PR мав позбавити. `pageSize: -5` або `page: -1` дають від'ємний `start`, і `slice` з від'ємними індексами повертає хвіст списку замість помилки. `pageSize: "20"` перетворюється на рядок: `start + pageSize` склеює рядки, наприклад `"20" + "20"`. `NaN` мовчки дає `[]`. В усіх цих випадках у відповіді неправильні дані, а не помилка.
- Також порушує: 13
- Як виправити: перевіряти, що `page` і `pageSize` є цілими (`Number.isInteger`), `page ≥ 1`, `1 ≤ pageSize ≤ MAX_PAGE_SIZE` (наприклад 100), а інакше кидати помилку. Додати тест на відхилення таких значень.

### 🔴 4. Нова публічна функція без запису в CHANGELOG — правило 6 · medium
- Де: `app/src/loans.js:30`
- Доказ: > `+export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`. Diff не торкається `app/CHANGELOG.md`.
- Що піде не так: з'являється новий експорт із формою відповіді `{ items, page, pageSize, total }`, але споживачі API не дізнаються ні про функцію, ні про семантику номера сторінки (з 0 чи з 1).
- Також порушує: —
- Як виправити: додати в `app/CHANGELOG.md` запис про `listLoansPage(db, user, { page, pageSize })`: форма відповіді, нумерація сторінок, межі `pageSize`.

## Потребує рішення людини
- Продуктивність. PR пояснює зміну тим, що «у UI все гальмує» на 3 000+ рядків. Але `listLoansPage` на кожен запит викликає `listLoans`, а той копіює всі рядки (`rows.map((l) => ({ ...l }))`), і лише потім береться `slice`. Порядок росту не погіршено порівняно з base, тому це не знахідка за правилом 19. Чи достатньо цього для UI, залежить від того, де саме гальмувало (рендер чи сервер), а з репо цього не видно.
- Коментар `Paged variant for the staff UI` не відповідає поведінці: функцію може викликати й учасник. Доступ при цьому коректний, бо виклик делегується до `listLoans` з тим самим `user` і учасник бачить лише свої позики. Чи потрібне обмеження `requireRole(user, STAFF)`, вирішує людина.
