## Знахідки
### 🔴 1. Email віддається без запису в журнал доступу — правило 2 · high
- Де: `app/src/loans.js:54`
- Доказ: > `+      email: db.findMember(l.memberId)?.email ?? null,`
- Що піде не так: бібліотекар викликає `overdueReport(db, iryna, "2026-10-08")` і отримує email учасників 1, 2 і 5 (позики 6, 3, 2). При цьому `db.accessLog` лишається порожнім. Правило вимагає по одному запису `logAccess(db, user, memberId, purpose)` на кожного учасника, чиї дані віддано, як це робить `memberCard` у `app/src/members.js:16`. Тут немає жодного запису, хоча звіт розкриває email кількох людей за один виклик.
- Також порушує: —
- Як виправити: після `requireRole` викликати `logAccess(db, user, memberId, "overdue-report")` один раз для кожного унікального `memberId` у звіті. Додати тест, який перевіряє, що кількість записів у `db.accessLog` дорівнює кількості учасників у звіті.

### 🔴 2. Нове поле `feeText` з `toFixed` і рядком «грн» — правило 4 · high
- Де: `app/src/loans.js:58`
- Доказ: > `+      feeText: (lateFee(l, todayIso) / 100).toFixed(2).replace(".", ",") + " грн",`
- Що піде не так: API повертає гроші як дробові гривні у форматованому рядку («110,00 грн»). Стандарт прямо забороняє в `src/` `toFixed`, дробові гривні й рядки на кшталт «15,00 грн»: форматування — справа клієнта. Клієнти почнуть розбирати цей рядок замість `feeKopecks`. Опис PR про це поле не згадує: він заявляє лише «ім'я та email», тож це незаявлена побічна зміна форми відповіді.
- Також порушує: 10 (побічну зміну не названо в описі)
- Як виправити: прибрати `feeText`. Клієнт форматує `feeKopecks` сам.

### 🔴 3. CHANGELOG не оновлено при зміні форми відповіді — правило 6 · medium
- Де: `app/src/loans.js:54`, `app/src/loans.js:58`; `app/CHANGELOG.md` у diff відсутній
- Доказ: > `+      email: db.findMember(l.memberId)?.email ?? null,` / > `+      feeText: ...`
- Що піде не так: експортована `overdueReport` тепер повертає ще два поля, `email` і `feeText`. У CHANGELOG досі описано старий набір полів: `loanId`, `member`, `book`, `daysLate`, `feeKopecks`. Споживачі API не дізнаються про нові поля, зокрема про персональне.
- Також порушує: —
- Як виправити: додати запис у `app/CHANGELOG.md` про поле `email` у `overdueReport`, зі згадкою про запис у журнал доступу.

### 🔴 4. Мапу імен замінено на лінійний пошук у кожному рядку — правило 19 · medium
- Де: `app/src/loans.js:53-54`; видалено `app/src/loans.js:49 (base)`
- Доказ: > `-  const names = new Map(db.members.map((m) => [m.id, m.name]));` → > `+      member: db.findMember(l.memberId)?.name ?? "—",` / > `+      email: db.findMember(l.memberId)?.email ?? null,`
- Що піде не так: `findMember` — це `members.find(...)`, тобто O(M). Раніше ім'я бралося з `Map` за O(1). Тепер для кожної простроченої позики виконуються два лінійні пошуки по учасниках, і складність зростає з O(L + M) до O(L·M). На засіяних 5 учасниках цього не видно, але на реальній бібліотеці з тисячами учасників і сотнями прострочень звіт помітно сповільниться. Та сама вартість подвоюється, бо пошук для одного рядка виконується двічі.
- Також порушує: 16 (дубльований виклик `findMember`; `lateFee` обчислюється двічі)
- Як виправити: залишити одну `Map` з `id` у `{ name, email }`, побудовану один раз перед `filter`, і брати з неї обидва поля.
