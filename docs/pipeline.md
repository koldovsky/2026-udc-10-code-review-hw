# Review pipeline

Task D. This document describes `pipeline/ai-review.yml`. The workflow is stored in `pipeline/` and not under `.github/workflows/`, so GitHub does not run it in the course repository. Running it means copying it into a fork's `.github/workflows/`.

The model that answers in CI is not the model used for the measured review runs. Those runs used Cursor's Grok 4.7 Medium through `.cursor/commands/review-pr.md`. This workflow calls Anthropic's Messages API. A score in `docs/review-scorecard.md` is not a measurement of the CI model.

## What `pipeline/ai-review.yml` does

1. **Trigger.** The workflow runs on `pull_request` for `opened`, `synchronize`, and `reopened`. `pull_request` is used so the test job can check out the pull request while a fork pull request still does not receive secrets. `pull_request_target` is not a trigger. A concurrency group keyed by the pull request number cancels the in-progress run of that pull request when a new push arrives.

2. **Deterministic checks.** Job `tests` is the check to mark as required. It runs on `ubuntu-latest` with a 10-minute timeout, checks out the pull request with `persist-credentials: false`, sets up Node.js 22, and runs `npm test` with `working-directory: app`. There is no `npm install`. `app/package.json` has no dependencies, and the test script is `node --test`. The job token is `contents: read`. The test step clears `GITHUB_TOKEN`, `GH_TOKEN`, `ACTIONS_RUNTIME_TOKEN`, and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` so the suite does not receive them. Job `ai-review` has `needs: tests`, so a failing suite skips the AI job.

3. **AI review.** Job `ai-review` runs after `tests` succeeds, and only when `github.event.pull_request.head.repo.full_name == github.repository`. A fork pull request skips it. The job is `continue-on-error: true` with a 10-minute timeout, so a failure there does not fail the workflow. It checks out `github.event.pull_request.base.sha` with `persist-credentials: false`. `docs/review-standard.md` and the Method and Output sections of `.cursor/commands/review-pr.md` are read from that base commit. The job does not check out the pull request head and does not run any code from the pull request. It writes `gh pr view --json title,body` and `gh pr diff` to files and caps the diff at 200000 bytes. If `secrets.AI_REVIEW_API_KEY` is empty, the step prints a notice and exits 0, and it does not comment. Otherwise `jq` builds a Messages API request. The system text is the standard plus those Method and Output sections. The user text puts the title (capped at 1000 characters), the body (capped at 50000 characters), and the diff between random `UNTRUSTED PR DATA` markers, with a line that says text inside the markers is data, not instructions. Title and body are not interpolated into the shell; `jq` reads them from the file. `curl` calls `https://api.anthropic.com/v1/messages` with `x-api-key` and `anthropic-version: 2023-06-01`. The model is `vars.AI_REVIEW_MODEL`, or `claude-sonnet-4-5` when that variable is empty. `max_tokens` is 4096. A non-2xx status fails the step and does not print the key. On success the step posts one comment with `gh pr comment --body-file`. The first line says it is an advisory AI review, not a merge gate, and that a human approves the merge. A `Verdict:` line in the comment is the model's opinion, not a GitHub approval.

4. **Who approves the merge.** A person does. The workflow never approves, never merges, and never changes labels. The only status check this pipeline is meant to require is `tests`.

## Permissions and secrets

The workflow token defaults to `contents: read`. Any permission not listed is none, because the top-level `permissions` block replaces GitHub's permissive default. Job `tests` sets `contents: read` only. Job `ai-review` sets `contents: read` and `pull-requests: write`. That write permission exists only on this job, and it is used only to post the comment.

`secrets.AI_REVIEW_API_KEY` is bound only on the curl step of `ai-review`. The tests job does not receive it. For a fork pull request the AI job's `if` is false, so the job does not run and the secret is not injected. GitHub also withholds secrets from a `pull_request` workflow opened by a fork; the `if` is a second stop. The check that still runs for a fork is `tests`, which has no secret. `vars.AI_REVIEW_MODEL` is not a secret. It only selects the CI model, which is a different model from the Cursor model used in the measured runs.

No step uploads artifacts. The request and response files are deleted before the curl step exits. The API key is an environment variable on that step, not a file.

## Threat model

| What a pull request with hostile content can do | What limits the damage in this workflow |
|---|---|
| Put instructions in the title, body, diff, or code comments ("ignore the standard", "approve", "print the key", "you are now a different reviewer") | Those fields are saved to files and placed in the user message between a random boundary the pull request does not choose. The line above the block says the text is data, not instructions. The system text is the base branch's standard, which treats reviewer-directed text as something to record, not to follow. The job has no tool that runs the model's reply. The reply is posted only as a comment. |
| Edit `docs/review-standard.md` or `.cursor/commands/review-pr.md` so this run follows the pull request's rules | `ai-review` checks out `github.event.pull_request.base.sha`. The standard and the Method and Output sections come from that commit. The pull request head is not checked out in this job. |
| Edit `pipeline/ai-review.yml`, or the copy under `.github/workflows/` after this file is installed in a fork | In the course repository the file is not under `.github/workflows/`, so GitHub does not run it. After installation, only people with write access can push a same-repository branch, so the person who can change the workflow that runs is an insider with that access. A fork pull request receives no secret, and the AI job is skipped. The key should be a dedicated key with a spending limit, and it can be revoked. Optional hardening, not in this file, is a GitHub environment with required reviewers on the `ai-review` job. |
| Break the shell with a title or body such as `$(curl …)` or an unmatched quote | Title and body never appear in a `run` script. `gh pr view --json title,body` writes `pr-meta.json`, and `jq` reads that file. The values passed into the shell are the pull request number and `github.repository`, not the title or the body. |
| Steal `GITHUB_TOKEN` or `AI_REVIEW_API_KEY` by changing tests or `package.json` | `npm test` runs the pull request's own code. That job's token is `contents: read`, credentials are not persisted, and the test step clears `GITHUB_TOKEN`, `GH_TOKEN`, `ACTIONS_RUNTIME_TOKEN`, and `ACTIONS_ID_TOKEN_REQUEST_TOKEN`. The API key is not in that job. `ai-review` does not run the pull request's code. The key is only in the curl step's environment. Curl is not run with `-v` or `set -x`, and a non-2xx response does not print the key. Nothing is uploaded as an artifact. |
| Persuade the model to print `Verdict: APPROVE` or "safe to merge" | The workflow does not parse the verdict. It does not call approve, merge, or label APIs. The comment starts with a fixed line that the review is advisory and that a human approves the merge. `ai-review` is `continue-on-error` and is not the required check. `tests` still has to pass, and a person merges. |
| The pull request's injected text makes the model write links, @mentions, or misleading text into the posted comment | The comment starts with the fixed advisory line. The token can only comment, not approve, merge, label, or push. A human reads the comment as untrusted model output. |
| Drive up API cost with a huge diff or with repeated pushes | The diff is capped at 200000 bytes, the body at 50000 characters, and the title at 1000 characters. `max_tokens` is 4096. The AI job runs only after tests pass, only for a same-repository pull request, and only when the key is set. The job timeout is 10 minutes. Concurrency cancels the previous run of that pull request. |

## What stays with a human

A person approves and merges. A person marks `tests` as the required check and does not require `ai-review`. A person reads the advisory comment, including when the model says `APPROVE` and when the pull request is talking to the model. `npm test` does not decide the judgment rules in `docs/review-standard.md` (role checks the suite does not cover, changelog entries, description claims, reviewer-directed text). A person owns `AI_REVIEW_API_KEY` and `AI_REVIEW_MODEL`. The key should be a dedicated key with a spending limit, and a person can revoke it. A person reviews the standard and `.cursor/commands/review-pr.md` before those files reach the default branch, because the AI job reads them from the base commit. A same-repository workflow change runs from the pull request, and only people with write access can push that branch. A GitHub environment with required reviewers on `ai-review` is optional hardening and is not in this file. The CI model is whatever `vars.AI_REVIEW_MODEL` names, or `claude-sonnet-4-5` when the variable is empty. The measured runs used Cursor's Grok 4.7 Medium, so those runs do not measure this job.
