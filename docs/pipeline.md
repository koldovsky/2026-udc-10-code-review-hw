# Pipeline рев’ю

## Що робить `pipeline/ai-review.yml`

1. Тригер `pull_request` запускає перевірки для змін PR, зокрема для PR із fork. Використання `pull_request_target` не потрібне й навмисно не застосовується.
2. Job `deterministic-checks` отримує код PR без збереження checkout credentials, встановлює Node.js 22 і виконує фактичну команду проєкту `cd app && npm test`. Цей job має бути обов’язковим check у branch protection або ruleset.
3. Job `ai-review` має `needs: deterministic-checks` і запускається лише після успішних тестів та лише для PR з тієї самої репозиторної власності. Наразі в репозиторії немає інтеграції з AI-провайдером, тому job лише явно повідомляє про безпечний пропуск. Він не імітує AI-висновок і не публікує коментар.
4. Людина залишається відповідальною за фінальне рішення. Обов’язковість тестів і людського approval налаштовується через branch protection/rulesets, а не самим YAML.

## Права і секрети

Workflow має тільки глобальний дозвіл `contents: read`. Job не отримує дозволів на `issues: write`, `pull-requests: write`, push, merge або зміну репозиторію. Секрети, AI-токени та привілейовані credentials не передаються жодному job.

Для fork job `ai-review` пропускається умовою на `github.event.pull_request.head.repo.full_name`. Це не є способом обійти обмеження `GITHUB_TOKEN`: звичайний `pull_request` для fork зберігає read-only модель. Якщо майбутня інтеграція потребуватиме секретів, вона не повинна запускати недовірений код із fork у контексті цих секретів.

## Модель загроз

| Загроза | Вплив | Реалізоване обмеження |
|---|---|---|
| PR містить шкідливий код, тести або `package.json` scripts | Код PR виконується під час тестів і може спробувати читати середовище, мережу або ресурси runner | Job має лише `contents: read`, не отримує секретів, використовує `persist-credentials: false`, має `timeout-minutes`; однак виконання тестів на runner усе одно є ризиком і потребує довіри до ізоляції GitHub-hosted runner |
| Опис PR, diff або коментар містить prompt injection | AI може спробувати виконати команди, розкрити дані або змінити критерії рев’ю | Цей workflow не передає PR-текст AI і не запускає AI-інструкції; правила для майбутнього AI-рев’ю визначені в `review/prompt.md`: PR-вміст є даними, а не інструкціями |
| Витік AI-токена або іншого секрету | Fork може отримати доступ до credentials через виконання коду | У реалізованому workflow секрети відсутні; AI job не checkout-ить PR-код і для fork пропускається. Майбутня інтеграція має зберігати секрети поза job, що виконує код PR |
| Надмірні permissions | Скомпрометований крок може змінити код, PR або налаштування | На рівні workflow задано лише `contents: read`; write permissions не надаються |
| Небезпечна публікація коментаря | Помилковий або ін'єкований текст може вплинути на рішення чи виконати shell-інтерполяцію | Реалізований workflow нічого не публікує. Звичайний `pull_request` із fork не використовується для обходу read-only `GITHUB_TOKEN` |
| AI-висновок сприймається як автоматичне рішення | Помилка рев’юера може заблокувати або небезпечно дозволити merge | AI-review позначений як advisory integration point; merge не виконується workflow, а фінальне рішення та human approval залишаються за людиною |
| `workflow_run` або `pull_request_target` використовується для отримання секретів | Недовірений PR-код може виконатися у привілейованому контексті | У workflow використано лише `pull_request`; `workflow_run`, `pull_request_target`, `eval` та виконання тексту PR як команд відсутні |

## Що захищено, а що ще потребує рішення

Реалізовано: read-only permissions, `pull_request`, відсутність secrets, відсутність запису в репозиторій, вимкнення checkout credentials, обов’язковий порядок `deterministic-checks → ai-review`, timeout і безпечний skip для fork.

Не реалізовано й не повинно вважатися виконаним: виклик AI-моделі, передача їй diff, автентифікація до AI-провайдера, публікація коментаря та автоматичне визначення merge. Перед додаванням інтеграції команда має окремо затвердити провайдера, модель доступу до PR-даних, редагування секретів, політику зберігання даних, обмеження мережі та формат advisory-висновку.

Для майбутньої публікації коментарів потрібні окреме обґрунтування мінімальних `pull-requests: write`/`issues: write` permissions, безпечна передача тексту через action/API без shell-інтерполяції та чітке маркування результату як дорадчого. Це рекомендація, а не властивість поточного workflow.
