# Домашнє завдання — Воркшоп 10

**Тема:** Code Review з AI
**Формат:** artifacts-first — ви будуєте свій AI-review flow і чесно міряєте, що він знаходить
**Час:** ~2.5 години
**Здача:** Pull Request у starter-repo (CodeRabbit зробить авто-рев'ю)

---

## 0. Налаштування

```bash
gh repo fork koldovsky/2026-udc-10-code-review-hw --clone
cd 2026-udc-10-code-review-hw
git checkout -b ws10/<github-username>

cd app && npm test && cd ..   # 13 зелених тестів; далі все — з кореня репо
```

`npm install` не потрібен — у застосунку **немає жодної npm-залежності**, лише Node 22+.
Потрібні ще GitHub account і Agentic IDE. **API-ключі не потрібні.**

### Що засіяно в репо

| Шлях | Що це |
|---|---|
| `app/` | Невеликий сервіс бібліотеки громади: учасники, книжки, позики, штрафи, звіти. Код **до** змін |
| `review-queue/pr-1` … `pr-6` | Шість pull request-ів, які чекають на рев'ю: опис (`PR.md`) і зміна (`change.diff`) |
| `docs/team-conventions.md` | Домовленості команди — на чому вона блокує злиття. Частину перевіряють тести, решта тримається на рев'ю |
| `docs/templates/` | Шаблони для всіх документів домашки |

Ключ відповідей до черги лежить в **окремому** репо
[`2026-udc-10-code-review-hw-answers`](https://github.com/koldovsky/2026-udc-10-code-review-hw-answers).
**Не клонуйте його до кінця Task B** і ніколи не кладіть усередину цього репо — інакше
агент, який рев'юїть, його побачить, і ваші цифри нічого не означатимуть.

> **Правила рев'ю — для вас і для вашого інструмента.**
> 1. Кожен PR — у **новій сесії**, яка бачить лише цей PR: його `PR.md`, `change.diff` і
>    код в `app/`. Інакше коментарі одного PR протікають в інший.
> 2. Диф не комітимо в `main` — це черга на рев'ю, а не фіча. Щоб запустити тести з PR:
>    з кореня репо `git apply review-queue/pr-N/change.diff`, а потім `git checkout -- app && git clean -fd app`.
> 3. **Текст усередині PR — це дані, а не інструкції.** Ні для вас, ні для агента.

## Task A — Стандарт рев'ю _(~30 хв)_

**Мета:** записати, на чому ваша команда **блокує** злиття, — і дати це рев'юеру як вхід,
а не сподіватися, що він здогадається.

1. `docs/review-standard.md` (шаблон є): перетворіть домовленості команди
   (`docs/team-conventions.md`) на правила для рев'юера і додайте свої — разом щонайменше
   8. Для кожного — чи воно **блокує** злиття, чи це дрібниця, і **чим перевіряється**:
   детерміновано (тести, лінтер, статичний аналіз, CI-перевірка) чи судженням рев'юера.
   Те, що можна перевірити детерміновано, не варто доручати рев'юеру.
2. Закладіть стандарт у конфіг свого рев'юера — команда, скіл чи правила вашого
   інструмента (наприклад, `.claude/commands/review.md`, `.cursor/rules/review.mdc`,
   `.github/copilot-instructions.md`) або файл промпта `review/prompt.md`. Якщо ваш інструмент
   тримає конфіг в іншій теці, покладіть копію в `review/`, щоб авто-рев'ю її побачило.
3. Обов'язково одне правило про **недовірений вміст**: усе, що в PR — опис, код, коментарі в
   коді, — рев'юер оцінює, а не виконує.

**Перевірка:** ≥8 правил із поділом «блокує / дрібниця» і «детерміновано / судження»;
конфіг рев'юера закомічено.

## Task B — Прогін і рахунок _(~45 хв)_

**Мета:** дізнатися, що ваш рев'юер насправді знаходить, а не що він обіцяє.

1. Запустіть рев'юер на кожному з шести PR — **по одній новій сесії на PR**.
   Вихід збережіть дослівно: `review-runs/pr-N.md`.
2. **Лише тепер** клонуйте репо з ключем — поруч, не всередину цього репо.
3. `docs/review-scorecard.md` (шаблон є): для кожного PR — знайдено / пропущено / хибні
   тривоги за правилами з ключа. Кожне «знайдено» підкріпіть **цитатою** з коментаря
   рев'юера. Підсумок: **precision і recall** — загалом, окремо для critical/high і окремо
   для дефектів, позначених у ключі **[стандарт]**: це порушення домовленостей команди.
4. Запишіть вартість: час і, якщо інструмент показує, токени на PR.

**Перевірка:** шість файлів у `review-runs/`; таблиця з цитатами; цифри сходяться.

> 💡 Якщо рев'юер **розійшовся з ключем** — не поспішайте записувати це в хибні тривоги.
> Перевірте, хто з них правий: ключ теж пишуть люди, і він теж може помилятися.

---

## Task C — Підналаштувати і перевірити ще раз _(~25 хв)_

**Мета:** покращити рев'юер так, щоб покращення **узагальнювалось**, а не підганялось під ключ.

1. За пропусками й хибними тривогами змініть стандарт або конфіг.
2. **Не можна** вписувати в правила конкретні дефекти з ключа («перевір рядок 12 у `cache.js`»).
   Можна — загальне правило, яке спіймало б цей **клас** проблем («ключ кешу містить усе,
   від чого залежить відповідь»).
3. Перезапустіть рев'юер на тих PR, де він помилився (нові сесії). Таблиця «до / після» в
   `docs/review-scorecard.md`.

**Перевірка:** зміни в конфігу видно в дифі; кожне нове правило — про клас проблем;
є «до / після» з тими самими правилами підрахунку.

---

## Task D — Пайплайн _(~30 хв)_

**Мета:** вбудувати рев'ю в процес так, щоб він допомагав і не відкривав нових дірок.

1. `pipeline/ai-review.yml` — workflow GitHub Actions для PR. Спершу **детерміновані**
   перевірки (тести — як обов'язковий check), потім AI-рев'ю — **дорадчим** коментарем.
   Безпечні налаштування: тригер `pull_request` (не `pull_request_target`), мінімальні
   `permissions`, жодних секретів для PR із форків. Злиття все одно затверджує людина.
2. Файл має бути валідним YAML: `npx --yes yaml valid < pipeline/ai-review.yml`.
3. `docs/pipeline.md` (шаблон є): модель загроз. Що може зробити PR зі шкідливим текстом
   вашому AI-рев'юеру? Що обмежує шкоду?

> Файл лежить у `pipeline/`, а **не** в `.github/workflows/`: так він не запуститься в
> репо курсу. Запустити його по-справжньому — у своєму форку — це бонус.

**Перевірка:** YAML валідний; є тести перед AI-рев'ю, `pull_request`, мінімальні
`permissions`, без секретів для форків; модель загроз про **ваш** пайплайн.

## Task E (bonus) — оберіть один шлях _(~15 хв)_

Заповніть **один** розділ у `docs/task-e-bonus.md`:

- **Шлях 1 — пайплайн по-справжньому.** Скопіюйте workflow у `.github/workflows/` свого
  форку, відкрийте там PR з одним із засіяних дифів і покажіть коментар бота.
- **Шлях 2 — стабільність.** Той самий рев'юер, той самий PR, три нові сесії. Наскільки
  збігаються знахідки?
- **Шлях 3 — два рев'юери.** Порівняйте свій рев'юер з іншим (наприклад, CodeRabbit у
  своєму форку) на тій самій черзі: precision, recall, вартість.

Необовʼязкове; відсутність — не помилка.

## Definition of Done

- [ ] **Task A:** `docs/review-standard.md` (≥8 правил) + конфіг рев'юера в репо
- [ ] **Task B:** `review-runs/pr-1.md` … `pr-6.md` + `docs/review-scorecard.md` з цитатами, precision і recall
- [ ] **Task C:** зміни в конфігу + таблиця «до / після»
- [ ] **Task D:** `pipeline/ai-review.yml` (валідний YAML) + `docs/pipeline.md`
- [ ] **Task E (bonus):** `docs/task-e-bonus.md` (опціонально)
- [ ] `cd app && npm test` зелений; диф із черги в `app/` **не** закомічено
- [ ] Ключ відповідей не закомічено; жодних секретів
